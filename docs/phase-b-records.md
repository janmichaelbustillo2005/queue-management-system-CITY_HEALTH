# Phase B: centralized records

Apply `backend/scripts/20261014-phase-b-records.sql` to an approved development Supabase project after Phase A and the consultation lifecycle migration. Never rerun the full schema/seeding SQL. This phase has not applied a migration to a live project.

The `/records` page contains Patients, Staff and User Accounts, with server pagination, search, filters, refresh, loading, error and empty states. Ticket retrieval returns the persisted visit with consultation timestamps; it does not recreate a historical printed ticket or its branding. Account activity is separately paginated. Patient search matches name or queue number, without exposing citizen identifiers. Date filters use Manila registration dates. Service and doctor filters match exact stored values. Staff filters use existing roles (`superadmin`, `admin`), positions derived from assignments (Super Admin, Admin, Doctor), and independent presence.

`patients` stores visits; there is no normalized patient profile table. This read-only module neither inserts identities nor merges patients based on names. Repeated visits remain separate historical rows. Staff and accounts both reuse `users.id_num`, because no separate staff profile exists. Display names fall back to the existing doctor assignment/account identifier. No Frontdesk role is invented. The current schema has no disabled flag or account creation timestamp: existing accounts are enabled, and creation dates are explicitly unavailable. Last login and seen come from Phase A sessions; old pre-Phase-A logins cannot be reconstructed.

Express validates custom JWT signature and the current persisted session, then requires `superadmin` for every records endpoint. Supabase Auth is not the application's identity source. RPC execution and raw patient/user table privileges are restricted to the backend service role; RLS is enabled and browser roles lose raw table privileges. The RPC has a fixed output whitelist, and responses use no-store caching. Existing queue/consultation operations are unchanged. Review other pre-existing SECURITY DEFINER functions separately when auditing the full deployment; this migration does not rewrite unrelated RPCs.

Login events are inserted atomically by a session-insert trigger. Logout is recorded only by the existing explicit, owner-bound logout RPC, once per session. Heartbeats, expiry, account changes and bulk administrative revocation never generate logout events. Historical activity is not fabricated. Activity starts at migration installation. Presence uses the existing 75-second timeout; valid unexpired sessions can be offline. Counter availability remains in existing dashboard monitoring.

Navigation: Dashboard; Queue Management; Doctor & Counter Monitoring (existing dashboard section); Records with Patients, Staff and User Accounts; Analytics; Settings. Existing system logo and responsive sidebar are reused. Account administration is not added to Records.
