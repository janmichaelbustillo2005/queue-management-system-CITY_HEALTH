# Phase 2.2 correction and development rollout guide

## Queue visibility and historical filters

Active queue responses include today's Manila registrations plus serving patients from any registration day. Previous-day waiting and terminal patients are excluded. A carried serving patient leaves the active response after completion; its saved consultation remains available through historical Records. Today's reset preserves older active consultations and their counter/acceptance state.

Records, Analytics and exports share historical filtering by registration date. A specific date covers that full Manila calendar day. A start/end range includes both calendar dates, implemented as an inclusive start and exclusive midnight after the end date. Empty/All Time filters are unrestricted. This Week means Monday through Sunday in Manila; This Month means the current calendar month. Explicit date/range fields override presets. Invalid dates, reversed ranges, unsupported presets and invalid doctors return 400.

Historical reads apply date, status and service predicates before fetching all ordered pages. Doctor filtering respects stored assignment, resolves existing counter aliases, and uses the existing service mapping for unassigned legacy rows. Records pagination and CSV use the same selected dataset. Analytics averages still use only valid completed actual start/end intervals; no inferred historical duration or AST prediction is added. Daily/hourly chart grouping uses Manila time and retains the year.

Queue Display reconciles pending events against each valid authoritative poll. It checks eligibility again before posting the combined bell/speech request, prunes withdrawn backlog events and ignores late older successful polls. Already posted bell/speech announcements complete normally. The selected slow descending bell now plays on the same local Python worker as speech, without a browser activation click.

Doctor monitoring pages show Accept only to an authenticated admin account whose doctor assignment resolves to that page's doctor. The Accept handler checks the same ownership condition before posting. Superadmin keeps monitoring information and the existing permitted cancellation action; Start/Complete ownership restrictions and backend authorization remain unchanged.

## Recovery considerations

The migration source adds UUID revision metadata to existing patients and replaces recovery functions; it contains no clinical timestamp backfill, patient/counter reset or inferred consultation start. Catalog verification does not independently prove preservation of every existing clinical row. Keep the Phase 2.1 revision metadata and trigger when reverting application code. If reverting the recovery function, keep Undo disabled and review the compatibility of both function definitions. Restoring the original first-free-counter behavior reintroduces the confirmed bug; the new wrapper deliberately rejects inconsistent outcomes. There is no automatic data rollback script.
